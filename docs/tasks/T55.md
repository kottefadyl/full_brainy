**T55 — Synchronisation des données en temps réel** · Dépendances : T52 (collections partagées), hébergement Vercel Hobby.
- Demande produit (12 novembre 2026) : les personnes qui modifient les mêmes collections devaient actualiser pour voir les changements des autres ; intégrer une synchronisation en temps réel compatible avec le plan gratuit de Vercel.
- Décision technique, vérifiée dans la documentation Vercel le 12 novembre 2026 : les WebSockets sont acceptés sur Hobby, mais une connexion ouverte garde une instance de 2 Go facturée à l'heure (360 Go-h gratuits, environ 180 h d'instance par mois) ; une seule personne qui laisse Brainy ouvert 8 h par jour dépasse le quota et Vercel suspend alors les fonctions 30 jours ; diffuser entre instances exigerait de plus un service Redis. Le canal en direct est donc **Cloud Firestore**, déjà dans le projet Firebase de Brainy (gratuit : 50 000 lectures et 20 000 écritures par jour) : Vercel ne garde aucune connexion ouverte.
- **Terminé quand :** une modification faite par une personne apparaît chez les autres personnes de la collection sans actualiser, sur le web, Android et Windows, sans connexion permanente sur Vercel, et personne ne lit le signal d'une collection qui ne lui est pas partagée.
- Fonctionnement : après toute mutation GraphQL réussie, l'API écrit un signal par collection touchée, `brainy_signals/{collectionId}` = `{ version, at, by, kind, readers }` (propriétaire et membres) ; aucun contenu ne quitte Brainy. Les clients se connectent à Firebase avec un jeton personnalisé (`realtimeToken`, uid = identifiant Brainy), écoutent les signaux où ils figurent parmi les lecteurs et rechargent sans indicateur de chargement la liste des collections et la première page ouverte ; plusieurs signaux rapprochés donnent un seul rechargement (600 ms) ; leurs propres changements sont ignorés ; une collection dont l'accès est retiré disparaît. Les règles `firestore.rules` réservent la lecture d'un signal à ses lecteurs et interdisent toute écriture aux clients.

Implémentation : API `src/realtime/` (`realtime.service.ts`, `realtime.interceptor.ts` global sur les mutations, `realtime.resolver.ts`), `src/firebase-admin-app.ts`, `AuthService.userIdFromToken` (sans lecture en base) ; `firestore.rules` et `firebase.json` à la racine. Web `lib/realtime.ts`, branchement dans `app/brainy-app.tsx`. Flutter `lib/realtime_sync.dart`, `lib/workspace_live_sync.dart`, dépendance `cloud_firestore`. `BRAINY_REALTIME=off` coupe la fonction ; sans compte de service Firebase, elle reste inactive.

Validé le 2026-11-12 : `npm run typecheck` ; `smoke:realtime` contre les émulateurs Firebase (Firestore et Auth) avec le vrai SDK client et les vraies règles : jeton, signal à la création et à la suppression, auteur, lecteurs, refus à une inconnue (requête et lecture directe), fin d'accès ; parcours Edge réel à deux personnes (entrée d'Awa visible chez Bruno en 0,9 s sans actualiser, suppression retirée) ; web `lint`, `tsc`, `build` ; Flutter `dart analyze`, test `realtime_sync_test.dart`, suite complète (273 tests), APK Android et application Windows construites.

Limites : la première page seulement est rechargée (les pages suivantes au prochain chargement) ; un même compte ouvert sur deux appareils ne se synchronise pas avec lui-même ; nécessite la base Firestore et la publication des règles (voir `docs/DEPLOIEMENT_VERCEL.md`) ; Android et Windows non essayés à l'écran.
