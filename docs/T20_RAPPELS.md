# T20 — Rappels liés aux entrées

Une entrée peut porter un rappel sur un de ses champs `DATE` ou `DATETIME` renseignés. L'utilisateur choisit l'avance (0 à 43 200 minutes), un fuseau IANA et un ou deux canaux : e-mail et notification push. Pour une simple date, il choisit aussi l'heure locale. Un événement récurrent reprend ses règles et ses exceptions ; le serveur calcule chaque échéance dans le fuseau de l'événement. Terminer une tâche annule ses rappels actifs. Modifier une entrée ou sa récurrence replanifie ses rappels ; supprimer l'entrée ou la collection les annule.

L'API enregistre les rappels et une ligne d'envoi par occurrence et canal. Chaque appareil push a sa propre ligne : l'échec d'un appareil ne renvoie pas les notifications déjà réussies aux autres. Un processus serveur vérifie les échéances toutes les 15 secondes, revendique le rappel en base, envoie, marque chaque livraison `SENT`, puis fait passer le rappel à l'occurrence suivante ou à `DONE`. Il réessaie les erreurs temporaires et peut marquer le rappel `FAILED`. Une relance normale du processus ne renvoie pas une occurrence marquée `SENT`. Avec SMTP et FCM, un arrêt exactement entre l'acceptation externe et l'enregistrement de `SENT` peut encore causer un doublon : aucun fournisseur ne garantit ici une transaction atomique avec MongoDB. Le `Message-ID` des courriels et le tag des notifications restent stables pour la même occurrence, mais un client de messagerie peut quand même présenter deux courriels.

## Configuration

Dans l'environnement de l'API, fournir `SMTP_HOST`, `SMTP_FROM`, et selon le serveur `SMTP_PORT` (587 par défaut), `SMTP_SECURE` (`true` pour TLS direct, généralement port 465), `SMTP_USER`, `SMTP_PASSWORD`. STARTTLS est exigé par défaut sur les autres ports (`SMTP_REQUIRE_TLS=true`) ; ne le désactiver que pour un serveur de test local. `docker-compose.yml` transmet ces variables depuis l'environnement ou un fichier `.env` local. Ne pas placer les secrets dans le dépôt. Vérifier l'adresse d'expédition autorisée par le fournisseur SMTP.

Pour le push, fournir `FIREBASE_PROJECT_ID` et `FIREBASE_SERVICE_ACCOUNT_JSON` (JSON du compte de service Firebase). En déploiement avec identité de charge de travail, `GOOGLE_APPLICATION_CREDENTIALS` peut pointer vers un fichier accessible au processus API ; il faut monter ce fichier dans le conteneur si Docker est utilisé. Le web demande `NEXT_PUBLIC_FIREBASE_VAPID_KEY`, la clé publique Web Push du même projet Firebase. Le service worker est servi à `/brainy-messaging-sw.js`. Le push web exige un contexte HTTPS ou localhost, un navigateur compatible et la permission de notification.

Flutter Android utilise l'identifiant d'installation Firebase et demande la permission de notification quand l'utilisateur active l'appareil. Le token est renouvelé à la connexion suivante et durant la session. Firebase doit être configuré sur l'application Android et les services Google doivent être disponibles. La configuration iOS du projet n'est pas présente ; Windows n'a pas de transport push natif dans cette tranche. Le courriel reste le canal utilisable sur ces plateformes si SMTP est configuré. L'interface n'active pas un canal sans sa configuration serveur et permet de retirer un appareil enregistré.
